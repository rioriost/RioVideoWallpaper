# GPT-6 Astra 設計・コードレビューと修正プラン

レビュー日: 2026-09-16

対象リビジョン: `7e96f44`

状態: レビュー時点の指摘と計画を保存。1.2.1 の修正・検証結果は末尾を参照。

## 対象と判断基準

アプリの起動・終了、動画再生、ディスプレイ別割り当て、生成エディタ、
プロンプト解釈、モデル、プロジェクト保存、Metal 描画、動画書き出しを対象とする。
最終コミットの差分だけでなく、現在の実装をレビューする。

- P1: データ消失、主要機能の破綻など、先に修正すべき問題。
- P2: 特定の入力・操作・環境で発生する機能上の問題。
- P3: 動作を直接壊さない整合性・保守性の問題。

コードから確認できる問題と、実機での追加確認が必要な事項を区別する。
修正は既存の機能を維持する小さな単位に分け、全面的な書き直しは行わない。

## 結論と修正優先順位

型付きの中間モデル、共通の描画処理、決定的な乱数・時計、
プレビューと書き出しの再利用という基本構成は維持してよい。
問題の中心は、責務の名前やファイル配置よりも、
**履歴・素材の所有関係、非同期処理の対象、時間・状態の契約**にある。

| 優先度 | ID | 問題 | 最初の対応 |
|---|---|---|---|
| P1 | L1 | 再書き出し・履歴削除が別の履歴の動画/サムネイルを壊す | revision 単位の不変素材と参照確認付き削除 |
| P1 | L2 | 不完全な履歴一覧で orphan cleanup を実行し、復旧可能な素材を削除する | 読み取り失敗時は削除中止、移動したライブラリの参照を保全 |
| P2 | E1–E3 | 出力結果の別プロジェクトへの混入、遷移直前の編集消失、手動編集の巻き戻り | 編集 session・revision・保存契約を明示 |
| P2 | R1–R3 | ループ不連続、空フレームの未クリア、プレビューと出力の残像不一致 | 数学的周期と描画状態を実出力で保証 |
| P2 | R4–R6 | 書き出し失敗時の待ち続け、異常寸法のクラッシュ、同一位置への再 seek 無視 | 終端状態・入力上限・コマンド識別子を追加 |
| P2 | W1–W3 | 可視画面の停止、旧設定移行漏れ、一部利用不能時の全体復元失敗 | 画面別判定と部分復元 |

## 履歴・素材管理の指摘

### L1 / P1: 履歴の識別単位と素材の識別単位が一致せず、別の履歴を壊す

該当箇所:

- `RioVideoWallpaper/Generative/Project/GeneratedAssetLibrary.swift:102-104`
- `RioVideoWallpaper/Generative/Project/GeneratedAssetLibrary.swift:142-148`
- `RioVideoWallpaper/Generative/Preview/GenerativeEditorView.swift:1655-1662`

履歴 JSON は日時付きで増える一方、動画 URL は
`Videos/<project.id>.mp4` に固定される。
同じプロジェクトを赤系で出力し、後で青系にして再出力すると、
赤系の履歴も青系の動画を参照するようになる。
再出力の作業先も既存の成功動画と同じなので、
失敗・キャンセル時に過去の成果物を失わない契約も成立していない。

また、履歴の削除は他の履歴からの参照を調べず素材を削除する。
動画だけでなく、再生成されずに引き継がれたサムネイルも共有されるため、
履歴一件の削除で残った履歴の素材が消える。

**再現結果:** コンパイル済みの実アプリのモデルを使い、
隔離したライブラリで履歴を2件作成して一方を削除した。
履歴は1件残るが、その履歴が参照する動画とサムネイルは両方消失した。
同一 project ID の異なる履歴 URL に対し、
`videoURL(for:)` が同じ URL を返すことも確認した。

**修正方針:** プロジェクト ID と保存 revision / asset ID を分離する。
出力は新規の作業 URL に行い、検証成功後に不変の成果物として公開する。
レコード削除と素材回収を分離し、参照が残る素材を回収しない。
参照元には履歴だけでなく、現在/未接続画面の壁紙割り当て、
旧形式設定、進行中の出力も含める。

**完了条件:** 同一 project ID の二つの出力が独立して再生できること。
二回目の失敗/キャンセル、一方の履歴の削除でも、他方の素材が変化しないこと。
共有サムネイルと現在使用中の壁紙も保護すること。

### L2 / P1: 読み取り失敗を「参照なし」と扱う cleanup が素材を削除する

該当箇所:

- `RioVideoWallpaper/Generative/Project/GeneratedAssetLibrary.swift:156-169`
- `RioVideoWallpaper/Generative/Project/GeneratedAssetLibrary.swift:192-195`
- `RioVideoWallpaper/Generative/Project/GeneratedAssetLibrary.swift:234-237`

履歴一覧は読み取り/デコードに失敗した JSON を除外する。
cleanup はこの不完全な一覧を完全な参照集合として扱うため、
読めなかった履歴にだけ関連する動画・サムネイルを孤立素材として削除する。
破損 JSON や一時的なアクセス障害の復旧後にも、素材は戻らない。

別の経路として、所有素材のパスが絶対パスで保存される問題もある。
ライブラリを移動して Settings で移動先を選んでも、
JSON の参照は移動前のままで、新しい場所の素材が孤立と判定される。

**再現結果:** 隔離したライブラリで保存済みレコードを破損させると、
一覧は1件から0件になった。
その後の cleanup は成功として終了し、動画1件・サムネイル1件を削除した。
破損 JSON だけが残った。実際のアプリのモデルによる再現である。
ライブラリ移動の経路はコードの参照解決から確認し、移動操作の実測は未実施。

**修正方針:** 一覧取得は成功したレコードだけでなく、
読めなかったレコードと理由も返す。
参照解析が完了しない場合、破壊的 cleanup は中止してユーザーへ通知する。
所有素材は root 相対パスまたは asset ID で保存し、
旧絶対パスを安全に移行する。移行中・作成中・使用中の素材は保護する。

**完了条件:** 有効/破損/未対応レコードが混在する場合に素材を削除しないこと。
ライブラリを実際に移動しても素材を解決でき、
移動後の cleanup でも参照中の素材が残ること。

## 編集状態・非同期処理の指摘

### E1 / P2: 出力完了を、開始時とは別のプロジェクトに関連付ける

該当箇所: `RioVideoWallpaper/Generative/Preview/GenerativeEditorView.swift:1772-1789`

出力開始時には `exportProject` をコピーするが、
完了時の URL 設定と自動保存は、その時点の可変な `project` を対象にする。
出力中も編集・履歴切り替えが可能なので、
A の出力中に B を開くと、B に A の動画が関連付く。
同じプロジェクトの色や seed を変えた場合も、設定と動画が一致しなくなる。

**修正方針:** 出力操作に project ID、revision、保存先 root を固定する。
結果は開始時のスナップショットへ保存し、
現在の編集状態への反映は revision が一致した場合だけ行う。
画面の消失・再生成をまたぐ task の所有者とキャンセル規則も明示する。

**完了条件:** 制御可能な exporter で処理を止め、
編集中の変更・別履歴への切り替え・保存先変更後に完了させても、
別の編集状態に結果が混入しないこと。

### E2 / P2: 自動保存の待機中に移動すると最終編集を失う

該当箇所:

- `RioVideoWallpaper/Generative/Preview/GenerativeEditorView.swift:1541-1547`
- `RioVideoWallpaper/Generative/Preview/GenerativeEditorView.swift:1627-1629`
- `RioVideoWallpaper/Generative/Preview/GenerativeEditorView.swift:655-657`

750ms の debounce は変更した時点のプロジェクトを保持せず、
実行時の `project` を保存する。
直後に別の履歴を開くと保存対象が置き換わり、
General タブへの移動などで画面が消えると保存 task はキャンセルされるだけである。

**修正方針:** dirty revision と保存対象スナップショットを編集 session に保持し、
履歴切り替え・画面消失前に確定保存する。
複数の変更から生じたサムネイル再生成要求も OR で蓄積して取りこぼさない。

**完了条件:** 変更から750ms未満での履歴/タブ切り替えでも、
元のプロジェクトの変更が一度だけ永続化されること。

### E3 / P2: 保存済みの手動編集を古い visualIntent で巻き戻す

該当箇所:

- `RioVideoWallpaper/Generative/Project/WallpaperProjectSanitizer.swift:42-50`
- `RioVideoWallpaper/Generative/Preview/GenerativeEditorView.swift:1530-1537`

`visualIntent` を持つプロジェクトで手動編集すると、
`renderParameters` は更新されるが古い intent は残る。
再読込時の sanitizer が intent からパラメータを再生成するため、
保存された Hue/Speed などが巻き戻る。

**修正方針:** intent を生成時の由来情報として扱うのか、
常に優先される編集モデルとして扱うのかを明確にする。
保存済みの明示的なパラメータを勝手に再マッピングしない。
必要なら手動 override / パラメータ revision を持たせる。

**完了条件:** intent 付きプロジェクトを手動編集し、
保存→読込→sanitize 後も編集結果が維持されること。
現在の UI にプロンプト生成の入口がないこととは別に、
intent 付きの保存プロジェクトを扱う契約として保証する。

## 描画・書き出しの指摘

### R1 / P2: 「厳密に周期的」という宣言に反して境界で絵が飛ぶ

代表箇所: `RioVideoWallpaper/Generative/Rendering/FieldLinesRenderer.swift:5084-5089`

Lissajous の時間位相を含む `curvePhase` に対してさらに `1.37` を掛けており、
speed=1 の一周で Y 位相が4.74周期進む。
時間を一周させても座標は元に戻らず、時計の modulo で急に先頭へ戻る。

実装の座標式を評価した反例では、seed=42、1920×1200 の curve0/sample0 において、
300フレーム時の境界移動は約390.5pxだった。
30,000フレームにしても約396.0px残り、
直前の一フレームの移動約0.409pxに収束しない。
これは数式による確認であり、動画から計測した値ではない。

同種の非整数時間係数や位相の単位混在は、
Soft Volumetric、Cyclic Automata、Kaleidoscope、
Constellation Drift、Aurora、Ink、Underwater、Sakura、
Snowfall、Nebula、Labyrinth、Luminous Strings にも見られる。

**修正方針:** normalized time と radians を区別し、
時間方向は整数調波、周期関数、境界で閉じる軌道で構成する。
family ごとの周期保証は実装と照合する。
`docs/RendererLoopMathematicalVerification.md` などの数学的保証も修正に合わせて更新する。

**完了条件:** 全67 familyについて代表 seed/パラメータを用い、
modulo 適用前の位相、境界の片側極限、実画像の境界変化を確認する。
`frame N == frame 0` だけでは時計の modulo により自動的に成立するので不十分。
粒子の生存期間や輝度も、位置と同じく境界を閉じる必要がある。

### R2 / P2: 頂点のないフレームで背景がクリアされない

該当箇所:

- `RioVideoWallpaper/Generative/Rendering/FieldLinesRenderer.swift:5953-5962`
- `RioVideoWallpaper/Generative/Rendering/FieldLinesRenderer.swift:7034-7036`

空の頂点配列で render encoder を作る前に return するため、
descriptor の `.clear` は実行されない。
Fireworks は境界で意図的に空配列を返すので、
黒くなるはずのフレームに以前の texture / pixel buffer の内容が残り得る。

**再現結果:** コンパイル済み renderer と64×64の Metal texture を使用した。
赤で初期化して frame 0 を描いても4096画素すべてが赤のままだった。
frame 30 では描画が行われるが、その後 frame 0 を描いても
直前の画像がそのまま残ることを確認した。GPU エラーは発生していない。

**修正方針:** 有効な空フレームでも clear/store pass を実行する。
「描く頂点がない」と「GPU 資源の確保に失敗した」を分け、
後者を成功した空フレームとして扱わない。

**完了条件:** 赤で初期化した texture に Fireworks の frame 0 を描き、
全画素が黒・不透明へ変わること。
通常フレーム後の黒い境界でも同じ結果になること。

### R3 / P2: プレビューの残像が表示頻度に依存し、書き出しと一致しない

該当箇所:

- `RioVideoWallpaper/Generative/Preview/MetalPreviewView.swift:169-180`
- `RioVideoWallpaper/Generative/Preview/MetalPreviewView.swift:231-236`
- `RioVideoWallpaper/Generative/Rendering/FieldLinesRenderer.swift:170-183`
- `RioVideoWallpaper/Generative/Rendering/FieldLinesRenderer.swift:1927-1940`

30fps設定に対してプレビューは60Hzで描画し、
同じ `frameIndex` でも毎回 fade と加算を行う。
Field Lines / Orbital の蓄積状態が書き出し時の一回/フレームと一致しない。
停止中の SwiftUI 更新による再描画でも蓄積が進み、
逆に描画遅延時には中間フレームの更新が飛ぶ。

**再現結果:** 実 renderer の64×64 textureで Field Lines の frame 17 を
二度描画すると、88画素の RGB が変化した。
蓄積を reset して同じフレームを描くと最初の画像と一致した。
同一フレームの重複描画が状態を変えることは GPU 上で確認できている。
60Hz の GUI と動画を並べた目視比較自体は未実施。

**修正方針:** 論理フレームの状態更新と、現在の画像の表示を分離する。
同じフレームの再表示では状態を変更せず、
遅延時は必要なフレームを順に進める。
seek・パラメータ変更時の状態再構成と warmup も同じ契約にする。
プレビューの青寄り背景と書き出しの黒背景も共有定義へ統一する。

**完了条件:** 同じ論理フレームを一回/二回表示した画像が一致し、
停止中の再描画で画像が変わらないこと。
連続更新、途中の表示省略、seek後の再構成と書き出しの結果が一致すること。

### R4 / P2: writer 失敗時に readiness 待ちから抜けられない

該当箇所: `RioVideoWallpaper/Generative/Export/GenerativeVideoExporter.swift:111-116`

`isReadyForMoreMediaData` の待機中に writer の status/error を確認していない。
writer が failed になり readiness が復帰しない場合、
後続の append / finishWriting の失敗検査へ到達できず、出力が待ち続ける。

**修正方針:** 待機中も失敗・キャンセルなどの終端状態を確認し、
明示的なエラーで終了して後始末する。
最終化・動画検証の前後にもキャンセルの境界を設ける。

**完了条件:** 注入可能な writer/input で not-ready→failed を作り、
有限時間でユーザーに失敗が通知されること。
最終化中のキャンセルも確認する。
なお、実ディスク枯渇と最終化中キャンセルの実挙動は今回未実測。

### R5 / P2: 巨大な正数の解像度が検証を通り、整数 overflow に到達する

該当箇所:

- `RioVideoWallpaper/Generative/Model/ExportSettings.swift:48-56`
- `RioVideoWallpaper/Generative/Export/GenerativeVideoExporter.swift:251-262`

幅・高さは下限だけを正規化するため、
巨大な正数を持つ履歴 JSON が読み込まれると、上限未検証のまま出力へ進める。
たとえば幅 `9223372036854775807`、高さ1200では、
ビットレート計算の `width * height` が Swift の整数 overflow で trap する。
通常のプリセット操作ではなく、異常な保存データから到達する問題。
この経路では FPS/時間には別の補正があるため、指摘対象は幅・高さとする。

**修正方針:** 対応できる解像度の上限を明示し、
読み込みと出力の両方で検証する。積には checked arithmetic を用い、
黙って補正せず理解可能なエラーを返す。

**完了条件:** 最大対応寸法は成功し、超過・極端な正数・不正寸法は
アプリを終了させず拒否されること。

### R6 / P2: 同じフレームへの新しい seek 要求を無視する

該当箇所: `RioVideoWallpaper/Generative/Preview/MetalPreviewView.swift:163-168`

「先頭へ移動→Play→数秒待つ→先頭へ移動」という通常操作でも、
前回と今回の要求がどちらも0なので二回目を無視する。
移動先の値を操作の識別子として兼用している。

**修正方針:** seek の要求 ID と移動先フレームを分離し、
同じ移動先でも新しい要求を必ず適用する。

**完了条件:** 同一位置への反復 seek と、
seek→編集による transport reset→同一位置への seek の両方を確認する。

## 再生・起動の指摘

### W1 / P2: 壁紙が見えている画面まで再生を停止する

該当箇所:

- `RioVideoWallpaper/PlaybackSuspensionPolicy.swift:38-58`
- `RioVideoWallpaper/VideoWindowController.swift:73-80`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:681-709`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:746-784`

被覆判定はウィンドウと画面の幅・高さしか比較せず、座標を保持していない。
さらに、いずれかの画面が被覆されたという結果で、すべての再生セッションを停止する。

たとえば 2560×1440 と 1920×1080 の二画面環境では、次の両方で全体停止になる。

1. 小さい画面だけを別アプリが覆い、大きい画面の壁紙は見えている。
2. 大きい画面上に 2000×1200 の通常ウィンドウがあり、どちらの画面も完全には覆われていない。

実際の `PlaybackSuspensionPolicy.swift` をコンパイルした独立プローブで、
どちらも `shouldSuspend == true` になることを確認した。

また、再判定の通知はアプリ切り替え・Space 切り替えなどに限定されている。
同じアプリ内で通常ウィンドウを縮小・閉じる操作では、
停止判定が次の通知まで更新されない経路がある。

**修正方針:** 画面とウィンドウの矩形を同一の座標系で扱い、
画面ごとの可視状態からセッションごとの停止状態を導出する。
同じ動画を複数画面で共有する場合、一画面でも壁紙が見えていれば再生を維持する。
被覆状態の変化を更新できる仕組みも用意し、
追加権限の要否と監視コストを確認して方式を選ぶ。

**完了条件:** 異なる解像度・上下左右配置・部分被覆・一画面のみの全画面表示・
通常ウィンドウの縮小/終了・画面スリープ/復帰を網羅する。
純粋な判定関数に加え、判定結果が各セッションに反映されることも確認する。

### W2 / P2: 起動経路が旧形式の保存設定を移行しない

該当箇所:

- `RioVideoWallpaper/RioVideoWallpaperApp.swift:109-117`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:394-406`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:444-481`

初期バージョンは `FavoriteVideoURL` に動画を保存していた。
現在も旧キーを読む処理は存在するが、起動時は新形式の
`restoreSavedDisplayAssignments()` だけを呼び、
移行処理を持つ `currentDisplayAssignments()` を使わない。

旧形式の設定だけが残るアップグレード環境では、
以前の壁紙を復元せずファイル選択を要求し、キャンセルすると終了する。

**修正方針:** 起動・設定画面・画面構成変更で共通の復元/移行処理を使用する。
ファイルへのアクセスを確認してから新形式の保存を確定し、
移行不能時も旧設定を失わないようにする。

**完了条件:** 旧 URL のみ、旧ブックマークあり、新形式あり、期限切れブックマーク、
アクセス不能ファイルの各ケースを、隔離した設定ストアで確認する。
正常な旧設定では、起動時に動画の再選択を要求しない。

### W3 / P2: 一つの動画がアクセス不能になると保存済み割り当て全体を復元できない

該当箇所:

- `RioVideoWallpaper/RioVideoWallpaperApp.swift:409-435`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:576-613`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:109-117`
- `RioVideoWallpaper/RioVideoWallpaperApp.swift:484-496`

復元時に、既定動画とすべての画面別動画へのアクセスを一括で要求している。
未接続画面の割り当ても含まれるため、ある動画が削除されたり、
保存先の外部ディスクが外れたりすると、利用可能な既定動画があっても
復元全体が失敗する経路がある。

その後の起動処理は新規選択に進み、動画を選び直すと画面別割り当てを空にして保存する。
一時的なアクセス不能と、新規ユーザー・設定破損を区別できていない。

**修正方針:** 保存された設定と現在再生可能な設定を分離する。
各割り当てを個別に復元し、アクセス不能な割り当ては保持したまま、
対象画面のみ既定動画へフォールバックするか、再選択を案内する。
一時的な切断だけで保存設定全体を上書きしない。

**完了条件:** 未接続ディスプレイ、取り外した外部ディスク、削除された生成動画、
再接続・再リンクを扱い、正常な画面の再生と保存設定が維持されることを確認する。

## 設計上の改善方針

### 再生と復元の状態を明示する

`AppDelegate` に集まっている設定復元、アクセス権管理、画面割り当て、
ユーザー通知を、必要な範囲で分離する。
特に「設定なし」「移行可能」「一部利用不能」「再生準備中」「再生失敗」は、
単一の `nil` やログだけで表現せず、呼び出し側が扱える状態にする。

初回起動時は外部動画の選択が必須で、キャンセルするとアプリが終了する。
生成機能だけを使いたいユーザーも開始できるよう、
壁紙未選択のまま設定/生成画面を開ける導線を検討する。
プロジェクトファイルからの起動でも、無関係な動画の選択を必須にしない。

### 編集 session と renderer の責務を分ける

約2,000行の `GenerativeEditorView` は表示と操作の接続を中心にし、
revision、保存待ち、出力 task、保存先へのアクセス寿命を
テスト可能な編集 session に集める。
単に巨大な View を複数ファイルへ分割するだけでは E1/E2 は解決しない。

約9,000行の `FieldLinesRenderer` は、
family ごとの形状/色の生成と共通の GPU 描画・蓄積状態を分離する。
最初から67個の新しいクラスを作るのではなく、
R1–R3 の検証に必要な時間・状態・出力契約を先に取り出す。

Settings の割り当て表示も、ローカル `@State` のコピーだけに依存させない。
`RioVideoWallpaperSettingsView.swift:119-124` の生成側で壁紙を変更しても
General 側が再取得されないため、共通の観測可能な割り当て状態、
または確実な変更通知/表示時再取得を用いる。

### UI と配布説明を実装に合わせる

現在のメニューバーは About / Settings / Quit という構成だが、
README と App Store の審査手順には、動画変更や Generate Wallpaper を
メニューバーから直接選ぶ旧導線が残っている。
修正時は英語・日本語の案内を現行の設定画面に揃える。

### 現行機能と未使用のプロンプト処理を区別する

現在の生成画面は renderer、seed、各パラメータを直接操作する UI であり、
`LocalVisualIntentProvider` / `PromptInterpreter` / `StylePreset` を
呼び出す製品コードの経路はない。
App Store の審査手順に残る「文章を入力して Generate」は現行実装と一致しない。
設計書に記載された将来構想と、実装済み機能を分けて説明する必要がある。

未使用のプロンプト API 単体では、部分一致による単語の誤解釈、
新規生成と追加編集の混同、67 family 中30種類への選択経路不足、
プリセットの色語の未対応を確認した。
ただし、これらを現行 UI の到達可能な不具合として主要指摘には含めない。
プロンプト機能を公開する場合に、生成/編集モード、欧文の単語境界、
family/別名の登録、構造化プリセットの契約を整備する。

### 周期性の保証範囲

Field Lines / Orbital は周期的な幾何信号を持つが、
残像の状態は有限 warmup による近似である。
この2 family は `isExactlyPeriodic = false` として明示し、
厳密な定常状態の保証とは区別した。残る65 family の周期契約とは同一視しない。
既存の出力動画は変更せず、式の修正は新しく生成する動画に適用する。
